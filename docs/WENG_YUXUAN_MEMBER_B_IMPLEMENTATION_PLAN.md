## 5 状态与时间设计

### 5.1 游戏状态

建议使用 `SurvivalState` 枚举，避免多个布尔值表达同一件事。

| 状态 | 含义 | 可进入的下一状态 |
| --- | --- | --- |
| `Ready` | 场景已配置，尚未进入有效游戏 | `Running` |
| `Running` | 时间、战斗与刷怪正常进行 | `Won` 或 `Lost` |
| `Won` | 完成 60 秒生存 | 重启后 `Running` |
| `Lost` | 生存结束前生命值归零 | 重启后 `Running` |

默认保留原版自动开局方式，不增加必须点击的开始页面。`Ready` 用于内部初始化。

`SurvivalGameManager` 是最终结果的唯一负责人。`Game3D` 的运行开关用于执行开始与停止，不再独立决定胜负或显示另一套结果。

### 5.2 倒计时

建议保持一个共同时间来源：

```text
ElapsedSeconds = Game3D.Spawner.ElapsedSeconds
RemainingSeconds = max(0, SurvivalDuration - ElapsedSeconds)
SurvivalDuration = 60 秒
```

`RemainingSeconds` 作为计算属性；不要另存一份独立累计的计时器再与生成器同步。时间采用游戏推进时间，按物理帧的 `delta` 累计；普通游戏中 `Engine.TimeScale = 1`。暂停、调试加速与机器卡顿时，需区分游戏时间和墙钟时间。

HUD 使用向上取整显示整数秒：开局 `60`，最后不足一秒显示 `1`，结束显示 `0`。胜利判定使用实际数值，不能依赖文字或取整后的结果。

### 5.3 同一物理帧的边界

建议生存管理器的物理检查排在玩家、敌人和弹丸更新之后。例如将管理器的 `ProcessPhysicsPriority` 设为 `100`，保持相关战斗节点为默认 `0`。Godot 按较小的物理处理优先级先执行，参见 [Node 官方文档](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node-property-process-physics-priority)。

每次检查先确认状态与生命值，再确认时间。建议同一物理更新内出现“生命值归零”和“时间到期”时按失败结算，并将这个离散时间边界约定写入测试。正常的提前死亡与健康存活到期必须分别正确处理。

结果仅允许从 `Running` 进入一次。连续死亡信号、多个伤害来源、重复时间检查均不能覆盖已经确定的结果。

## 6 管理器的属性与方法草案

以下接口已实现。类名和公开入口保持与分工约定一致。

| 定义 | 类型或签名 | 用途 |
| --- | --- | --- |
| `SurvivalDuration` | `double`，默认 `60.0` | 正式游戏使用 60 秒；自动测试可临时缩短并恢复配置 |
| `State` | `SurvivalState`，外部只读 | 当前状态 |
| `RemainingSeconds` | `double`，计算属性 | 从共同时间计算剩余秒数 |
| `_game`、`_player` | `Game3D`、`Player3D` | 配置后保存的对象引用 |
| `_restartPending` | `bool` | 防止连点按钮安排多次重启 |
| `Initialize(game, player)` | `void` | 接收有效对象并订阅开始事件 |
| `OnRoundStarted()` | `void` | 初始化本局状态并发布初始 UI 数据 |
| `CheckRound()` | `void` | 游戏进行中检查生命值和时间 |
| `FinishRound(result)` | `void` | 单次结算、停止战斗、发布结果 |
| `RestartRound()` | `void` | 检查允许重启并安排一次安全重启 |
| `TimeChanged` | `Action<double>` 事件 | 通知 UI 最新剩余时间 |
| `StateChanged` | `Action<SurvivalState>` 事件 | 通知 UI 状态和结果 |

`Game3D` 建议增加 `RoundStarted` 事件，在初始开局和每次 `StartGame()` 复位完成后各发出一次。保留 `StartGame()` 与 `StopGame()` 的现有调用方式，以兼容成员 A 的测试和代码。

同时增加只读属性 `Game3D.IsRunning`，读取现有 `_running`，使管理器能够判断协调器是否已停止，避免暴露可写运行开关。`CheckRound()` 先检查管理器是否为 `Running`，再处理生命值归零；玩家仍存活时，只有协调器也处于运行状态才检查时间并推进 HUD。

原有 `EndWithDefeat()` 调整为把失败交给管理器统一结算。正常游戏的终局调用均经过管理器；直接调用 `StopGame()` 仍应能安全停止协调器，而不会随后被计时检查误判为胜利。直接停止属于内部控制接口，不用来显示结果；若未来增加暂停功能，应单独设计暂停状态及恢复入口。

## 7 玩家脚本的具体修改

### 7.1 保留现有玩法

保留 WASD 移动、鼠标瞄准、左键射击、射击请求事件、玩家死亡事件和竞技场碰撞设置。生存模式允许玩家战斗。

第一轮保留原版数值作为基准：最大生命值 `100`，速度 `7` 个世界单位/秒，射速 `5` 发/秒，受伤后无敌时间 `0.6` 秒。先跑通整局，再根据记录调整玩家参数。

### 7.2 参数和生命值事件

将最大生命值和移动速度从私有常量改为可配置属性，例如 `[Export]` 的 `MaxHealth`、`MoveSpeed`。验证生命值和速度参数为有效正数。射速和无敌时间暂沿用原版，除非试玩证明有调整必要。

新增 `HealthChanged(currentHealth, maxHealth)` 信号。有效受伤后与 `ResetPlayer()` 复位完成后分别通知 HUD；被无敌状态或非活动状态忽略的伤害不需要重复通知。HUD 初次绑定还应主动读取当前值，避免错过早期事件。

致命伤害先把生命值和玩家活动状态更新完整，再发出生命值变化与死亡通知；管理器接到死亡通知后统一结算。这样 UI 回调读取到的对象状态与显示值一致。

现有 `Health` 的默认值引用了常量 `MaxHealth`。改成实例导出属性后，需改为在初始化/复位方法中设置 `Health`，避免在 C# 实例属性初始化器里引用另一个实例属性。

信号沿用项目现有 C# `[Signal]` 声明方式，见 [Godot C# 信号文档](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_signals.html)。

### 7.3 重置内容

`ResetPlayer()` 要检查：位置回到 `(0, 0.5, 0)`，速度归零，生命值恢复当前最大值，射击冷却和无敌时间归零，瞄准方向与角色朝向复位，旧鼠标位置缓存清空，`Active = true`，`Visible = true`，发出生命值更新。

当前实现已清理 `_hasMousePosition`、`_mousePosition` 和角色朝向。重启时若射击输入仍按住，需要先释放，再允许新一局射击。

## 9 初始化与结束的统一流程

### 9.1 开局

Godot 子节点的 `_Ready()` 在父节点之前执行。HUD 的 `_Ready()` 可以查找自身控件，但管理器不能假定此时 `Game3D.Spawner` 已经由父节点创建。此生命周期顺序参见 [Node 官方文档](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node-private-method-ready)。

建议父节点 `Game3D._Ready()` 按以下顺序组织：读取 Player/Entities，创建并配置成员 A 的生成器，连接敌人和弹丸事件，取得管理器及 HUD 引用，初始化管理器，绑定 HUD，连接失败入口，最后调用 `StartGame()`。

`StartGame()` 完成复位和启动后发出 `RoundStarted`，管理器进入 `Running`，HUD 显示 60 秒及满生命值。订阅与初始化只做一次，重启不重复订阅。

### 9.2 结束

管理器确认仍是 `Running` 后确定结果，停止游戏协调与刷怪，设置玩家不活动，将 `Entities` 的处理模式设为禁用，再通知 HUD 显示结果。

单独停止生成器只会阻止新增敌人。现有弹丸仍有自己的 `_PhysicsProcess()`，因此要同时停止实体更新，保证结束界面期间弹丸和战斗不会继续推进。UI 与管理器放在 `Entities` 之外，仍可响应重启。

冻结最终显示时间与结果；后续伤害、敌人死亡和重复检查不再更新本局结果。

## 10 重启流程

优先复用成员 A 的 `Game3D.StartGame()`，避免另写一套实体清理和生成器复位。按钮只向管理器请求重启。

建议过程：检查终局状态，设置一次性重启门闩并禁用按钮，安排安全的延迟调用，调用 `StartGame()` 完成复位；由 `RoundStarted` 恢复管理器与 HUD，最后释放门闩。

| 复位项 | 负责位置 | 验收标准 |
| --- | --- | --- |
| 旧敌人及弹丸 | `Game3D.ClearEntities()` 与生成器清理 | 旧实体立即脱离场景，后续释放；不会参与新一局碰撞 |
| 实体处理模式 | `Game3D.StartGame()` 集成 | 从禁用恢复为正常继承处理 |
| 玩家 | `Player3D.ResetPlayer()` | 满血、初始位置、可见、可操作、冷却及瞄准缓存复位 |
| 刷怪 | 成员 A 的 `Spawner.Start()` | 时间归零、数量归零、间隔恢复为初始阶段 |
| 生存状态 | 管理器处理 `RoundStarted` | `Running`，剩余时间 60 |
| 击杀与分数 | `Game3D.StartGame()` | 均归零 |
| HUD | `OnRoundStarted` 和初始数值刷新 | 隐藏结果面板，时间与生命值恢复 |
| 事件连接 | 初始化阶段 | 多次重启后仍只有一套有效订阅 |

若后续使用整场景重载作为备选，应了解 [SceneTree 重载接口](https://docs.godotengine.org/en/stable/classes/class_scenetree.html#class-scenetree-method-reload-current-scene)，并在现有回调外安全执行。本次建议先使用已有开始接口。
